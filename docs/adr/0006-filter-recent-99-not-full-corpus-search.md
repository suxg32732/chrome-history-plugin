# 搜索框只过滤已加载的最近 99 条，且刻意不复刻 Chrome 的搜索语义

v0.4.0 用户要求「顶部增加搜索过滤框，可以根据条件搜索历史记录」。决定：在弹窗顶部增加**单一关键词**的搜索框，它只对**已加载的最近 99 条**做本地过滤，**不**调用带 `text` 的 `chrome.history.search` 去检索全量历史；匹配采用**不区分大小写的子串匹配**，作用于标题与网址。也就是说，插件实现的是**关键词过滤 (Keyword Filter)**，而非**全量检索 (Full-corpus Search)**——后者的职责继续归 `chrome://history`（ADR-0004）。

理由：①延续 ADR-0004 划定的插件边界，零新权限、零新失败模式，且可做成纯函数沿用现有无头测试缝；②子串匹配在 99 条的小语料下更符合直觉，对中文（无空格分词）尤其明显；③Chrome 的 `text` 查询在 Chromium 中是**全表暴力扫描**（`SELECT ... FROM urls WHERE hidden = 0`，无 LIMIT，逐行断词），成本随历史库总量增长且与 `maxResults` 无关——「输入即过滤」在这种代价下不可接受。

**Considered Options**：

- **把关键词交给 `text` 检索全量历史 — 否决**：推翻 ADR-0004 的插件定位，与底部「显示所有历史」职责重叠；且如上所述，每次击键触发一次全表扫描，只能退化为回车触发或防抖，复杂度与不确定性显著上升。
- **在前端复刻 Chrome 的「分词 + 前缀（≥3 字符）+ AND」语义，以求与内置页结果一致 — 否决**：需 ICU 断词边界，纯 JS 只能近似复刻；且 3 字符阈值等隐藏规则会带来反直觉行为（2 个汉字退化为精确匹配），而 Chrome 官方文档从未承诺这套语义（仅存在于 Chromium 源码）。
- **不在前端计算，过滤一律交给 API — 否决**：语义天然与内置页一致，但丧失纯前端过滤的零延迟与可测试性，且每次查询仍是一次暴力扫描，等于付出 B 的代价却只得到 A 的语料范围。
- **关键词过滤 + 子串匹配 — 采用**：最小改动、最快响应、最易测试，且明确定义了「插件不做什么」。

**Consequences**：

- 插件搜不到第 99 条之外的记录；该需求由底部「显示所有历史」跳转 `chrome://history` 承接。
- **插件与 `chrome://history` 对同一关键词的结果会不一致**（插件更宽松，例如搜 `domain` 插件能命中 `example.org`，内置页不能）。这是有意为之，**不要当作缺陷「修复」**。
- 语料（最近 99 条）与取数层不变：`fetchRecentRecords` 无需改动，`RECENT_LIMIT = 99` 继续有效。
- 过滤只改变展示，不改变数据获取时机——弹窗打开时仍只发一次 `chrome.history.search` 请求。
- 若将来要支持全量检索，需新 ADR 取代本条与 ADR-0004 的相应部分，而非就地扩展本过滤框。
